# Architecture

## Overview

lasrs-cpp is a wrapper, not a port. All format work (LAS parsing, the LAZ
arithmetic codec, COPC hierarchy) is done by the Rust crate `las` (las-rs)
and its LAZ backend `laz` (laz-rs). This repository adds three thin layers
on top:

```
+----------------------------------------------------+
|  C++ API    include/lasrs/*.hpp                    |  header-only, C++20
|             namespace las, RAII, exceptions        |
+----------------------------------------------------+
|  C ABI      include/lasrs/lasrs.h                  |  generated by cbindgen
|             opaque handles, status codes           |
+----------------------------------------------------+
|  Rust shim  rust/src/*.rs (crate lasrs_ffi)        |  staticlib
|             extern "C" functions, catch_unwind     |
+----------------------------------------------------+
|  Upstream   las (laz-parallel feature), laz, rayon |  from crates.io
+----------------------------------------------------+
```

Users link one static library (`lasrs_ffi`) and include the headers. The
final application has no Rust runtime dependency and no extra DLLs.

## API design: mirror las-rs

The C++ API uses the las-rs names so that las-rs users can switch without
relearning anything: `las::Reader::from_path`, `reader.header()`,
`read_points`, `fill_points`, `las::Builder`, `las::PointDataBuilder`,
`las::CopcReader::query`, `las::point::Format`, `las::copc::VoxelKey`, ...
Only what las-rs offers is exposed; lasrs-cpp adds no features of its own.

Translation rules:

| Rust | C++ |
|---|---|
| `X::new(...)`, `From<T>` | constructor |
| `Result<T>` | `T`, errors throw `las::Error` |
| `Option<T>` | `std::optional<T>` |
| `&str`, `&[u8]` borrowed from an object | `std::string_view`, `std::span` (valid while the object lives) |
| `String`, `Vec<u8>` fields | `std::string`, `std::vector<uint8_t>` |
| lazy iterators | `std::vector` |
| enum with data used as an argument (`LodSelection::Level(2)`) | class with static factories (`LodSelection::Level(2)`) |
| enum with data used as a value (`GeoTiffData`) | `std::variant` |
| method on a data-less enum | free function in the same namespace |
| `impl Read + Seek`, `impl Write + Seek` | `std::istream&`, `std::ostream&` (must outlive the object) |
| `NaiveDate`, `Uuid` | `std::chrono::year_month_day`, `std::array<uint8_t, 16>` |

Objects owned by Rust (`Header`, `PointData`, `Reader`, `Writer`,
`CopcReader`) are RAII handles. `Header` and `PointData` are copyable
(deep copy through `clone`); readers and writers are move-only. Plain data
(`Point`, `point::Format`, `Vlr`, `Bounds`, `Transform`, `Builder`, ...) are
C++ structs with the same public fields as in Rust.

Small pure helpers (`Transform::direct`, `Bounds::grow`, `Vlr::is_crs`,
`VoxelKey::child`, ...) are implemented inline in C++ to avoid an FFI call
per value; everything else calls into Rust.

`Builder` keeps the Rust builder it was created from, so fields that las-rs
does not make public (bounds, point counts) survive
`Builder(header).into_header()` exactly as in Rust.

## Performance rules

The language boundary costs a few nanoseconds per call. It only matters if
it is crossed per point. Therefore:

1. **Batch everything.** Reading, writing, columns and point decoding move
   whole `PointData` batches. Per-point calls exist only where las-rs has
   them (`Writer::write_point`, `Header::add_point`).
2. **Zero copy where possible.** `PointData` stays in Rust memory;
   `raw_bytes()` and `resize_for()` expose it directly as a `std::span`.
   Columns and points are decoded in one call into a C++ buffer.
3. **Parallelism lives in Rust.** One `fill_points` call decodes many LAZ
   chunks concurrently on the rayon pool.

## FFI rules

1. **Opaque handles.** `LasrsReader*`, `LasrsWriter*`, `LasrsHeader*`, ...
   are created by Rust and released only through `lasrs_*_free`.
2. **No cross-allocator frees.** Memory allocated by Rust is freed by
   Rust; memory owned by C++ is never freed by Rust.
3. **No panics across the boundary.** Every fallible export runs inside
   `catch_unwind` and returns a `LasrsStatus`.
4. **Error details.** On failure a thread-local message is stored;
   `lasrs_last_error()` returns it and the C++ wrapper throws it as
   `las::Error`.
5. **Plain C types only.** Fixed-width integers, `double`, `bool`,
   pointers and `size_t` lengths. Strings are UTF-8 pointer + length;
   paths are converted to UTF-8 by the C++ wrapper.
6. **Streams.** C++ streams are passed as a context pointer plus
   callbacks. Callbacks never throw. Seeking past the end behaves like a
   file (reads return nothing, writes zero-fill), because the LAZ reader
   and writer rely on it.
7. **ABI version.** `las::abi_compatible()` compares the header's
   `LASRS_ABI_VERSION` with the linked library's `lasrs_abi_version()`.

## Build

- CMake drives everything. Corrosion (fetched with FetchContent) invokes
  cargo, builds the shim as a static library and exposes it as a CMake
  target, including the system libraries a Rust staticlib needs.
- `rust-toolchain.toml` pins the Rust version; `Cargo.lock` pins crates.
- Dependencies are optimized even in Debug builds (`[profile.dev.package."*"]`)
  so debug builds still decode LAZ quickly.
- `CMakePresets.json` provides `debug` and `release`.
- The C header is regenerated by cbindgen and committed, so users never
  need cbindgen; CI checks that it is up to date.

## Distribution (planned)

No package is needed. The product is a compiled bundle: the static library
`lasrs_ffi` plus `include/lasrs/`. Users either build it from source (CMake
+ Corrosion, requires Rust) or take a prebuilt bundle, and link it like any
C/C++ static library. Nothing is published yet.
